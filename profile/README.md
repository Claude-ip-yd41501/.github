<h2>一、实验怎么设：只动一个变量</h2>
<p>对照实验最容易失败的地方是同时改了两三样东西，最后不知道是哪个起的作用。这里只允许一个变量变：出口。设备、浏览器、账号、操作时间、任务内容全部保持一致，否则结果没法归因。</p>
<h3>分两组，一组当前环境一组候选出口</h3>
<p>A 组用你现有的出口，作为基线；B 组用待评估的住宅出口。两组各准备两到三个账号，账号的新旧程度尽量接近——一个新号一个老号混在一起，结果会被账号本身的差异带偏。同一个账号不要两组来回切，切了登录地就乱了。</p>
<h3>固定操作脚本，别自由发挥</h3>
<p>把每天的动作写成固定脚本：上午登录网页端发三次中等长度提问，下午解析一份十页左右的文档，晚上做一次登出重登。每个动作记录开始时间、完成时间、是否出现验证、是否断流。脚本固定了，两组的差异才可比。</p>
<p>只在上午测等于没测。晚八点到十一点是线路最容易拥塞的时段，很多候选出口白天表现漂亮，晚上抖得没法用。实验期至少包含两个完整晚高峰，否则结论不成立。</p>

<h2>二、干净度怎么量化：四项检测</h2>
<p>"干净"不是形容词，它有几项可以查到的客观证据。四项都过才算基本干净，任何一项不过就先别放量。检测本身花不了多少时间，熟练之后一条地址五分钟。</p>
<h3>检测一：ASN 是否指向住宅运营商</h3>
<p>用 whois 或任意 IP 情报站查 ASN 名称与归属组织。指向宽带运营商、有线电视网络、光纤入户服务商的，属于住宅属性；指向云厂商、数据中心、CDN、托管商的，即使供应商说"家宽"，也要打问号。这一项最容易露馅，也最该先查。</p>
<h3>检测二：类型标签是否一致</h3>
<p>拿两三个不同的 IP 情报库交叉查 residential、business、hosting、proxy 标签。三个库结论一致最可信；出现分歧时按更严格的那个算，因为平台侧用的模型往往比公开库更保守。</p>
<h3>检测三：历史滥用记录</h3>
<p>查公开黑名单与滥用投诉库，重点看最近九十天。有批量注册、撞库、爬虫类投诉记录的地址，即使现在无人使用，也可能已经被降权。查的时候顺手看一眼同 C 段的其他地址，整段都被标记的，单条再干净也不建议用。</p>
<h3>检测四：同址并发与共享情况</h3>
<p>这一项查不到，只能问，或者用行为反推：连续几天在不同时段观察延迟曲线，如果曲线呈现出与你无关的规律性波动，很可能是有人在同时使用。直接问供应商单条地址允许几个并发，回答含糊的就当共享处理。</p>

<h2>四、结果怎么读：三条判定线</h2>
<p>数据拿到之后不要凭印象下结论，用三条线卡一下，过线就继续，不过线就回去问供应商或者换一家。三条线的顺序有讲究，先看安全类指标，再看体验类指标。</p>
<h3>第一条：验证次数不高于基线</h3>
<p>这是最硬的指标。B 组验证次数明显高于 A 组，说明候选出口的环境不如现有环境，其他指标再好也没意义。注意区分"首次登录验证"和"运行中验证"，前者是正常流程，后者才是问题信号。</p>
<h3>第二条：晚高峰首屏可用耗时不超过基线的 1.3 倍</h3>
<p>用中位数比较，不用平均值，避免一次极端卡顿拉偏结论。1.3 倍是个宽松但有意义的线：超过它，日常操作会明显感到迟钝。超过两倍基本可以判定这条线路不适合交互式使用。</p>
<h3>第三条：48 小时内流式中断不超过两次</h3>
<p>长回复、长文档解析对连接稳定性最敏感。中断频繁说明线路存在丢包或超时问题，这类问题在短测里看不出来，在真实使用中很折磨人。中断次数超标时，先排查是不是本地网络问题，排除后再归因到出口。</p>

<h2>五、什么时候可以从试用走到放量</h2>
<p>试用通过不等于可以立刻全量。放量本身会改变环境：并发数上去了，单条出口的压力也上去了，原本稳定的线路可能因为承载过多而暴露问题。所以放量要分批，每一批留观察期。</p>
<h3>第一批放三成，观察三天</h3>
<p>先把三成账号迁到新出口，其余保持原状。三天里重点看验证次数有没有上升、有没有账号出现异常提示。这一批的作用是验证"多条并发同时跑"的情况，单条试用测不出这个。</p>
<h3>第二批再放三成，第三批收尾</h3>
<p>第二批通过后，剩下的可以按周分批迁完。每批之间留两三天，不要一次迁完。全部迁完之后保留一条旧线路做备用，至少留一个月，确认新环境没有滞后性问题再撤。</p>
<h3>什么情况下应该放弃这次采购</h3>
<p>两种情况建议直接放弃：一是四项检测里有任意一项明确不过且供应商无法换址；二是七天观察期内出现两次以上非预期验证且无法解释成因。这两条任一成立，继续投入只会把问题推到放量之后。</p>

<h2>常见问答</h2>
<h3>试用两三天够不够判断？</h3>
<p>答：能判断明显问题，判断不了长期稳定性。两三天足以发现 ASN 不对、验证频繁、晚高峰卡顿这类硬伤；但地址漂移、周期性拥塞、供应商后台变更这类问题往往要一周以上才显形。建议至少跑满七天低强度观察。</p>
<h3>同一批账号能不能两组都用？</h3>
<p>答：不建议。同一个账号在两条出口之间切换，登录地会来回跳，验证次数必然上升，这个上升是实验设计造成的，不是出口质量造成的。分组用的账号要分开，且两组的账号新旧程度尽量接近。</p>
<h3>检测发现是机房段但速度很快，能用吗？</h3>
<p>答：取决于用途。纯数据抓取、对身份一致性要求不高的场景，机房段的速度优势明显；但涉及账号登录与长期会话的场景，机房段被识别的概率高得多。速度不能替代属性，属性不对，快也没用。</p>
<h3>供应商不给试用怎么办？</h3>
<p>答：可以退一步买最小额度，按小时或按天买一两条，成本很低。连最小额度都不提供的，等于要求你先付整月再验证，这种交易结构本身就不对等。市场上能给短周期试用的供应商并不少，没必要冒这个险。</p>
